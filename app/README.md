# app — AC Server Manager (backend)

**Purpose:** API HTTP (FastAPI + SQLModel/SQLite) que crea, configura, arranca y vigila servidores de Assetto Corsa (`acServer` nativo
de Kunos), con control en vivo por el protocolo UDP ACSP. Cada módulo es un router `/api/v1/...` (se agrupan en `api/v1/__init__.py`);
no hay endpoints «solo para la UI». Subcarpetas: `live/` (ACSP, tiempos en vivo — su README),  `api/` (router versionado), `admin/` (página HTML).

## Files

| Módulo | Qué es / lo no obvio |
|---|---|
| `main.py` | App FastAPI. `lifespan` abre la BD, re-engancha (`adopt`) los acServer que sobrevivieron a un reinicio, lanza los bucles de fondo (`schedule.run_forever`, `wake.run_forever`, parada por inactividad, purga de métricas) y los cierra. `GET /healthz`, `GET /admin/servers`. Monta la SPA (`web.mount_spa`) al final si `ACM_SERVE_UI`. |
| `config.py` | `Settings` (pydantic-settings, prefijo `ACM_`): `host`, `port`, `data_dir`, `db_path`, `serve_ui`, `cors_origins`, `acserver_cmd`, `port_range_start/end` (9600–9700, bloques de puertos por servidor), `log_lines`, `download_hosts`, `idle_stop_seconds` (0 = nunca), `discord_status_webhook`, `discord_webhook`, y para el bot/vinculación `discord_bot_token`, `discord_channel`, `discord_role`, `discord_client_id`, `discord_client_secret`, `public_url`. |
| `db.py` | Motor SQLite (WAL, `foreign_keys`), `init_db()` (crea tablas y `_add_missing_columns`: añade columnas nuevas a tablas existentes sin migraciones; cuidado con tipos como `AutoString`), `get_session`. |
| `models.py` | Tablas: `User`, `Token` (sesiones y tokens API en una sola tabla), `Setting` (clave/valor JSON: `announcement`), `User` (con `discord_id` y `timezone`, IANA, por defecto `America/Mexico_City`), `Ban`, `LeagueMember` (plantel de una liga, con `non_racing`), `LeagueSuspension`, `Rsvp` (respuesta de un usuario de Discord a un anuncio: `schedule_id`+`discord_id`, `user_id` si vinculó su cuenta, `status` yes/maybe/no), `Server` (puertos, `csp_extra`, `weather_plan`, `wake`, `integrity`, `integrity_extras`, `welcome`, `session` = última `SessionIn` aplicada, sin la contraseña de admin…), `Event` (`is_default`, `derived`, `league_id`), `Schedule`, `ContentSeal`, `Penalty`, `Activity`, `Championship`, `ChampionshipEvent`. |
| `auth.py` | Usuarios y roles (`admin` > `steward` > lectura), login por cookie o `Authorization: Bearer`; `guard(role)` es la dependencia que protege routers; hash de contraseñas y de tokens (solo se guarda el hash). `PATCH /auth/me {timezone}` guarda la zona del navegador (validada con `zoneinfo`); la BD guarda todo en UTC y la zona solo sirve para mostrar. |
| `servers.py` | CRUD de servidores, reparto de puertos (`_alloc_base_port`: TCP/UDP/HTTP/plugin), render de `server_cfg.ini` y `entry_list.ini`, `SessionIn`/`apply_session` (aplica una sesión completa —guarda `Server.session`; el reloj de sesión solo se reinicia si cambian duraciones/pista/bucle o se reinicia de verdad, así el autoguardado del panel no lo toca—: pista, autos, tiempos, opciones, inscritos, bienvenida; opcionalmente reinicia), `start_server`/`stop`, ajuste `wake`, y los comandos en vivo (`chat`, `kick`, `next_session`, `restart_session`, `admin`). Rutas steward: lecturas y moderación; escritura admin. |
| `supervisor.py` | Un proceso `acServer` por servidor, en su propia sesión y con la salida en `server.log`, para **sobrevivir a reinicios del manager**; `adopt()` lo reconoce por `server.pid`. El socket ACSP se abre con `Instance.connect_acsp`: el servidor se registra **antes**, y si el puerto local está ocupado reintenta (3 veces y luego cada 5 s en segundo plano) en vez de dejar un acServer sin dueño; el socket se cierra cuando el proceso termina solo. Mientras no hay ACSP, `Instance.logboard` (`live/logboard.py`) da la clasificación leyendo el log. `Instance` guarda cliente ACSP, buffer de logs y estado. |
| `wake.py` | **Puerto HTTP público** (juego+1) siempre del manager, no de acServer (el de acServer es `http_internal` = `port_range_end` + índice del bloque, abierto en el firewall porque el ping UDP del juego lo nombra): con el servidor en marcha reenvía `/INFO` y `/JSON|…` a acServer (la respuesta se reutiliza `UPSTREAM_TTL` = 5 s: cada juego pregunta al lobby cada ~15 s y cada pregunta cae en el bucle principal de acServer, que los avisos «CPU overload» delataban) cambiando su `cport` por el público, y responde `/api/details` (la página del *wrapper* de Content Manager: la info del lobby + `description` = descripción/bienvenida del servidor). Servidor apagado que «parece abierto»: `Waker` ocupa además el puerto de juego, responde el ping UDP (`0xC8`) y sirve `/INFO` y `/JSON|guid` con la misma forma que acServer; un intento de entrar por TCP desde una dirección que consultó el lobby (UA «Assetto Corsa Launcher», 15 min) lo enciende. `before_start` libera el puerto de juego; el HTTP sigue contestando durante el arranque. |
| `timeline.py` | Reloj de sesión del servidor «apagado»: calcula en qué sesión y minuto estaría y, al arrancar de verdad, lo salta a esa posición (`resume`, vía ACSP `SET_SESSION_INFO` + `NEXT_SESSION`). La posición se lee **antes** de arrancar. |
| `schedule.py` | Arranques programados: recordatorios a Discord, inicio del evento a su hora, parada al terminar (`duration_min`), `open_window` (ventana en la que `wake` está permitido), rechazo 409 por solapes. `tick` cada pocos segundos. `_rsvp`: publica una vez el anuncio con el bot (`Schedule.rsvp_message`), y en cada tick convierte las reacciones ✅/❔/❌ en filas `Rsvp` (con varias reacciones gana la nueva; quitarlas todas borra la fila), enlaza `user_id` por `User.discord_id` y edita el mensaje con los contadores solo si cambian. `Schedule.notes` (≤1000) es la sección «Notas» del anuncio (`info` también se añade ahí); `ScheduleOut.rsvp` = cuentas; `GET /schedules/{id}/rsvps` = quién (steward). |
| `events.py` | Eventos guardados = **presets**: una `SessionIn` completa con título; `run_event` la aplica y reinicia el servidor; `duplicate`. `Event.is_default` (a lo sumo uno; `POST /events/{id}/default` lo mueve) es el preset del que parte un evento nuevo del calendario. `Event.derived` marca la copia que crea el calendario para un evento (no es un preset editable ni puede ser el predeterminado). Al guardar, `EventIn` valida la lista de inscritos: cada auto debe estar entre los `cars` de la sesión, ningún Steam ID repetido y una lista cerrada necesita al menos uno (en `EventIn`, no en `SessionIn`, para que los presets antiguos sigan cargando). |
| `content.py` | Índice de autos y pistas instalados, checksums, `build_entry_list`, descarga/subida en zip, subida por partes (`/uploads`, `PUT` con `offset`, `complete`) y desde enlace (`/uploads/from-link`). |
| `download.py` | Descarga desde MediaFire, Google Drive o Dropbox directo al VPS (lista blanca `download_hosts`, límites de tamaño y redirecciones). |
| `integrity.py` | Sellos MD5 de lo que acServer comprueba (`surfaces.ini` del sistema, `surfaces.ini` y `models.ini` de la pista, `data.acd` de cada auto) + extras. **Se sellan solos:** `seal_installed` al instalar un auto/pista (`content._extract`; una reinstalación resella) y `seal_new` al arrancar el manager (lo instalado sin sello). Modo por servidor `off/warn/require` (puerta antes de arrancar) y vigilancia de «checksum» en el log (`on_log_line`). |
| `results.py` | Lee `results/*.json` de acServer a clasificación normalizada; `apply_penalties` reordena con las sanciones. |
| `penalties.py` | Sanciones del comisariado, guardadas aparte del resultado (tipos: tiempo, posiciones, DSQ, parrilla, puntos); aviso a Discord. En un resultado de una liga con catálogo, `POST` acepta `item` (nombre del catálogo → tiempo o DSQ; la razón es opcional, se antepone el nombre), `GET …/catalogue` lo lista, y no se admiten sanciones de puntos. |
| `csp.py` | Opciones extra de servidor de Custom Shaders Patch (`Server.csp_extra`, un INI: `[SCRIPT_n]`, `[EXTRA_RULES]`…): se esconden al final del mensaje de bienvenida (INI en UTF-8 → zlib → base64 sin `=` → tras 32 tabuladores y `$CSP0:`; formato documentado por los autores de CSP). `welcome_with_extra` lo escribe en `cfg/welcome.txt` (`servers._write_instance`) al arrancar o aplicar una sesión; `PUT /servers/{id}/csp_extra {text}` (admin) lo guarda y sobrevive a los cambios de sesión (la bienvenida normal no). El juego original solo muestra el texto de bienvenida. |
| `requirements.py` | Lo que el piloto debe tener instalado: build de Custom Shaders Patch que pide la liga (`csp_build`, 0 = ninguna) y descargas (`items`: nombre + enlace, p. ej. Helicorsa), en `Setting` `requirements`. `GET/PUT /requirements` (steward lee, admin escribe). Se **muestra, no se impone**: la forma documentada de exigir CSP (TRACK = `csp/<build>/../<pista>`) no sirve con el acServer nativo de Linux (abre `content/tracks/csp/<pista>` y pierde `surfaces.ini` y los checksums; probado), y acServer tampoco puede imponer una app. Aparece en la ficha del servidor en Content Manager (`wake.details` lo añade a la descripción) y en el anuncio (`{requisitos}`). |
| `bans.py` | Expulsar y vetar por Steam ID en todos los servidores (steward). `Ban` (tabla): quien tenga ese Steam ID es expulsado en cuanto se conecta, en cualquier servidor (`acsp.ACSPClient._apply` pregunta `is_banned`; métrica `ban_kick`) y al momento si ya está dentro. No depende de la lista negra de acServer: vale también para un servidor que se despierte, y quitar el veto surte efecto al instante (el vetado llega a conectar un instante antes de la expulsión). `GET/POST /bans`, `DELETE /bans/{guid}`, `POST /players/{guid}/kick` (expulsa de donde esté; puede volver). |
| `championship.py` | Campeonato = **liga**: tabla de puntos, carreras contadas (clasificación calculada al leer, con sanciones aplicadas) y las reglas de liga: `practice_required` / `practice_laps` / `practice_days` (requisito de práctica) y `penalties` (catálogo `[{name, seconds, dsq}]`, `PenaltyItem`). `PATCH` solo cambia lo enviado. `standings` devuelve por piloto puntos, victorias, podios, carreras y puntos de sanción. Las estadísticas generales del servidor no pertenecen a ninguna liga. |
| `league.py` | Plantel de una liga (`LeagueMember`: Steam ID, nombre, equipo, auto preferido, `exempt`): `GET/POST /championships/{id}/members` (lista con las vueltas válidas de la ventana y si entra), `DELETE …/{guid}`. `valid_laps` cuenta `Activity` `lap` con `cuts == 0` del piloto en los últimos `practice_days` días (cualquier servidor y pista; las vueltas anteriores a que se guardara `cuts` no cuentan). `session_for(sess, ev, at)`: para un `Event` con `league_id` devuelve la sesión con la lista cerrada = plantel elegible (bloqueada, sin `pickup`; el auto del miembro si está entre los del evento, si no el primero) y avisa por Discord (`alert`) de quién queda fuera; 409 si nadie entra. `count_results(sess, sc, ev, until)` cuenta, para la liga de un evento, los resultados de tipo Race que su programación dejó en la carpeta de resultados del servidor entre el inicio y `until` (idempotente; `ChampionshipEvent.event_id` dice de qué evento vienen): un evento del calendario con liga —borrador o publicado— es así una carrera que cuenta, sin elegir archivos; lo llama `schedule.tick` para las programaciones en curso o terminadas hace menos de 2 días. **Suspensiones** (`LeagueSuspension`, `GET/POST /championships/{id}/suspensions`, `DELETE …/{id}` la levanta; admin escribe): `ban` (hasta levantarla), `time` (`days`), `races` (fuera de las próximas N carreras), `qualy` (N carreras sin clasificar: `acsp` los expulsa mientras el servidor está en clasificación —`qualy_banned`, solo con un evento de liga en curso—, y salen últimos) y `grid` (N lugares de parrilla). `session_for` deja fuera de la lista a los de `ban/time/races`. `count_results` cuenta también los resultados `Qualify` (`ChampionshipEvent.session_type`; no puntúan): cada uno convierte las suspensiones `grid` en un `Penalty` de tipo `grid` calculado desde donde clasificó entre los que corren, y lo que no cabe (ya está cerca del final) queda en `places_left` para la siguiente clasificación; cada Race contado resta una carrera a `races` y `qualy`. `LeagueMember.non_racing` (safety car, dirección de carrera, caster): no cuenta para los lugares perdidos (`apply_penalties(..., non_racing)` los saca de la parrilla), ni para el requisito de práctica, ni puntúa en la clasificación, ni puede ser suspendido. Lo llaman el arranque programado y `wake` (`schedule.py`) y `events.run_event`. |
| `metrics.py` | Registro de actividad (`log`) y agregados (`summary`, `activity`, `now`); `purge` por antigüedad. |
| `discord.py` | Webhooks: estado del servidor (arrancó/paró/cayó), `announce` (anuncios de liga), `alert`, mensajes de sanción. **Bot** (REST, sin gateway): `rsvp_post/edit/read` (publican/editan el anuncio —un payload de mensaje de Discord— con las tres reacciones, lee quién reaccionó; máx. 100 por emoji). **Vinculación OAuth2** (`scope=identify`): `GET /auth/discord/link` (con sesión iniciada, redirige a Discord; `state` en memoria 10 min), `GET /auth/discord/callback` (guarda `User.discord_id`, 409 si ya es de otro usuario, y reclama sus `Rsvp` previos), `DELETE /auth/discord` (desvincula). |
| `announcement.py` | El mensaje del anuncio de inscripción como **JSON editable** (`{"content": "...", "embeds": [...]}`, el formato de Discord) con `{variables}` (`VARS`: `title`, `server`, `clima`, `clima_line` (el clima de la sesión, p. ej. «Lluvia fuerte»; vacío si no hay), `track`, `cars`, `start`, `horario`, `formato`, `reacciones`, `counts`, `yes/maybe/no`, `notas`…; un `{nombre}` desconocido se queda como está). `variables(...)` las calcula de `Event.data` y el `Schedule` (la práctica abre en `start_at`; clasificación y carrera siguen una tras otra); `render` sustituye, colapsa líneas en blanco, corta `content` a 2000 y fuerza `allowed_mentions: {parse: [roles]}` (nada de @everyone); `validate` rechaza claves que no sean `content`/`embeds`, vacío o >6000 caracteres. Guardado en `Setting` (clave `announcement`); sin nada guardado se usa `DEFAULT`. `GET /announcement` (plantilla, defecto y variables; steward), `PUT` (admin), `DELETE` (vuelve al defecto), `POST /announcement/preview` (con datos de ejemplo, no publica). Un cambio llega a los anuncios ya publicados en el siguiente tick (`schedule._rsvp` los reedita). |
| `telemetry.py` | `POST /telemetry/ingest`: recibe lo que manda la app dentro del juego (`clients/OPRTelemetry`) y lo mezcla con el mapa en vivo. Público (identifica por SteamID64). |
| `web.py` | `mount_spa`: sirve `app/static` (frontend compilado) con respaldo a `index.html`. |

## Interactions
- **Inbound:** el sitio web de la liga (`OPR WP/acm/manager_api.py`, token en servidor), la UI React (`web/`), `clients/`, `deploy.sh`.
- **Outbound:** procesos `acServer`, UDP ACSP, Discord, descargas externas; disco: `data/acmanager.db`, `data/content/{cars,tracks}`, `data/instances/<id>/` (cfg, results, `server.log`, `server.pid`).
- **Variables de entorno:** todas `ACM_*` (ver `config.py` y el README raíz).
- **Puertos:** bloque por servidor desde 9600 (juego TCP/UDP, HTTP público = juego+1, plugin local) y un puerto HTTP interno de acServer por bloque desde 9700 (`ufw allow 9700:9724/tcp`).

## Flow — «Iniciar sesión» desde el panel
1. `POST /servers/{id}/apply` con `SessionIn` → `servers.apply_session` valida contenido (`_check_content`), escribe los INI y, si `restart`, detiene y arranca.
2. `start_server` → `integrity.gate` → `wake.before_start` (libera puertos) → `timeline.resume` (lee la posición) → `supervisor.start`.
3. `supervisor` crea el proceso, el cliente ACSP se conecta y `timeline` coloca la sesión donde toca.
4. Los resultados llegan a `results/` y se leen con `results.parse_result_file` + `penalties`.
